## 2026-08-31 — 별도 백엔드(Express/FastAPI)를 두지 않는다

Next.js Route Handler가 백엔드 역할을 전부 한다.

버셀 배포가 전제인데 백엔드를 분리하면 배포 대상 2개, CORS, 쿠키 도메인,
환경변수 2벌, 로컬 프로세스 2개가 따라붙는다. 1인용 앱에서 이는 순수 비용이다.
Route Handler로도 API 키는 서버에만 남으므로 보안 목표는 동일하게 달성된다.

**되돌리려면:** 라우트 핸들러의 로직이 이미 `lib/` 아래 순수 함수로 분리돼 있으므로
FastAPI/Express로 옮기는 것은 어댑터 작성 수준이다.

## 2026-08-31 — Redis 대신 Postgres 단일

TTL 자동 만료는 `expires_at` 컬럼 + 조회 시 비교로, 원자적 카운터는
`UPDATE ... SET n = n + 1 RETURNING n`으로 Postgres에서 동등하게 구현된다.
저지연은 사용자 1명에게 의미가 없다. 계정·환경변수·장애지점을 하나 줄이는 이득이 더 크다.

**되돌리려면:** `SessionStore` 인터페이스에 `RedisSessionStore` 구현체를 추가한다.
라우트 코드는 바뀌지 않는다.

## 2026-08-31 — 세션이 아니라 예산 카운터가 진짜 방어선

원래 요구사항은 "세션 종료 시 API 원천 차단"이었다.
하지만 세션이 살아있는 15분 동안은 호출이 무제한이므로, 프론트의 `useEffect`
의존성 실수 하나로 인증된 세션이 초당 수십 번 호출을 낸다.
**세션은 "누가"를 막지 "얼마나"를 막지 않는다.**

그래서 방어를 4겹으로 나눴다 — 세션 게이트 / DB UNIQUE 멱등성 / 예산 카운터 /
OpenAI 계정 하드 리밋. 이 중 비용의 대부분을 잡는 것은 **멱등성 제약**이다.

## 2026-08-31 — "당일 추가 생성 없음"을 DB 제약으로 구현

프론트 규칙이나 서비스 계층 검사가 아니라 `study_days`의
`UNIQUE (subject, day_no)` + `UNIQUE (subject, study_date)` 두 제약으로 강제한다.

프론트 규칙은 버그로 뚫린다. DB 제약은 안 뚫린다.
새로고침을 100번 해도 LLM 호출은 정확히 1회다.

## 2026-08-31 — 하트비트 ping을 넣지 않는다

세션 생존을 알리는 주기적 ping은 흔한 패턴이지만 여기서는 **기능을 정확히 무력화한다.**
탭이 열려 있는 한 유휴 타임아웃이 영원히 갱신되어 "자리 비움 차단"이 사라진다.

`idle_expires_at`은 실제 학습 행동(콘텐츠 요청, 답안 제출, 정리본 저장)에만 밀린다.
대신 클라이언트에 남은 시간 카운트다운을 표시하고 만료 2분 전 배너를 띄운다.

## 2026-08-31 — 다듬기(polish)에도 재시도 상한을 DB 제약으로 건다

## 2026-08-31 — Next 16 이 계획과 다른 지점 두 곳

뼈대를 세우고 `node_modules/next/dist/docs/` 를 읽어 확인한 것.

1. **`export const runtime = 'nodejs'` 를 쓰지 않는다.** Next 16 에서 nodejs 가 기본값이고
   Edge 런타임은 deprecated 다. 문서가 이 export 의 제거를 명시적으로 권한다.
2. **동적 라우트의 `params` 는 Promise 이며 두 번째 인자(context)로 온다.**
   따라서 `withSession` 가드가 context 를 핸들러까지 그대로 넘겨야 한다.
   원래 계획은 `new URL(req.url).pathname.split('/')[3]` 로 세그먼트를 잘라 쓰려 했는데,
   경로 구조가 바뀌면 조용히 깨지는 방식이었다.

**교훈:** 프레임워크 메이저 버전이 학습 데이터보다 새로우면 추측하지 말고
`node_modules/<pkg>/dist/docs/` 를 먼저 읽는다. 이 규칙을 `CLAUDE.md` 에 넣었다.

## 2026-08-31 — 비밀 검사를 부정 목록이 아니라 허용 목록으로

`check:secrets` 를 "모든 파일에서 NEXT_PUBLIC_ 금지"로 짰더니 **검사기 자신의 테스트 파일을

문제는 "이 문자열이 어딘가 있다"가 아니라 **"클라이언트 번들에 도달한다"** 이다.

## 2026-08-31 — argon2id 대신 node:crypto 의 scrypt

스펙 §3.5는 argon2id를 명시했으나 구현 단계에서 scrypt로 바꿨다.

argon2 npm 패키지들은 네이티브 모듈(NAPI)이라 버셀 서버리스 번들링에서 깨질 위험이 있다.
`node:crypto` 의 `scrypt` 는 표준 라이브러리이고 메모리 하드 KDF 로서
비밀번호 하나를 지키기에 충분하다. 의존성 0개, 배포 위험 0개.

저장 형식에 파라미터를 함께 넣었다(`scrypt$N$r$p$salt$hash`)므로
나중에 비용을 올려도 기존 해시를 계속 검증할 수 있다.

`verifyPassword` 는 확신할 수 없는 모든 경우에 false 를 준다.
특히 `AUTH_PASSWORD_HASH` 가 비어 있을 때 반드시 false 여야 한다 —
여기서 true 가 나오면 인증이 통째로 무력화된다. 이 경우를 테스트로 못박았다.

**되돌리려면:** `lib/auth/password.ts` 두 함수만 교체한다. 호출부는 바뀌지 않는다.

## 2026-08-31 — DB 연결을 지연시킨다

`lib/db/client.ts` 를 모듈 최상위에서 `DATABASE_URL` 을 검사하고 던지도록 짰다.
"런타임에 조용히 실패하는 것보다 빌드에서 큰 소리로 깨지는 게 낫다"는 판단이었는데
**틀렸다.**

Next 빌드는 라우트 모듈을 import 해서 설정을 수집한다. 그래서 첫 라우트를 추가한
순간 `npm run build` 가 깨졌다 — DB URL 없이는 빌드도, CI 도, 타입 검사도 못 돈다.

Proxy 로 감싸 첫 사용 시점에 연결하게 바꿨다. import 는 항상 성공하고,
실제로 쿼리를 날릴 때 같은 메시지로 실패한다. 두 경우 다 테스트로 못박았다.

**교훈:** "빌드에서 깨지는 게 낫다"는 빌드가 그 코드를 실행하지 않을 때만 맞는 말이다.

## 2026-09-01 — 세션 상태 라우트를 폴링하지 않는다

`GET /api/session/status` 는 `withSession` 가드 뒤에 있고, 가드는 통과할
때마다 유휴 만료를 15분 뒤로 민다. 세션 바가 이걸 주기적으로 부르면
**넣지 않기로 한 하트비트가 뒷문으로 들어온다** — 자리를 비워도 세션이
영원히 살아 있게 된다.

그래서 세션 바는 마운트 때 한 번만 부르고, 그 뒤로는 받아온 만료 시각과
로컬 시계의 차이를 1초마다 다시 그린다. 서버에 묻지 않는다.

카운트다운을 클라이언트 자체 타이머로 굴리지 않는 이유는 따로 있다 —
탭이 백그라운드로 가거나 노트북이 잠들면 `setInterval` 이 어긋난다.
기준은 항상 서버가 준 시각이다.

`tests/session/status-route.test.ts` 에 "상태 조회도 유휴 만료를 민다"를
테스트로 박아뒀다. 폴링을 붙이려는 사람이 먼저 읽으라고 둔 것이다.

## 2026-09-01 — 다시 묻는 방아쇠는 타이머가 아니라 사람이다

## 2026-09-01 — 비밀번호 해시 구분자를 `$` 에서 `.` 으로

**증상:** 맞는 비밀번호를 넣어도 전부 거부됐다. 로그인 화면은 "비밀번호가
틀렸다"만 보여줬다.

**원인:** Next 의 dotenv 로더는 **변수 확장을 한다.** 해시 형식이
`scrypt$16384$8$1$salt$hash` 였는데, `$16384` · `$8` · `$1` · `$salt…` 를
전부 환경변수 참조로 보고 빈 문자열로 치환했다.

```
파일에 적힌 값    : 조각 6개, 길이 83
앱이 읽은 값      : 조각 1개, 길이 25   "scrypt6384-bda_kLQQrOKzgA"
```

`verifyPassword` 는 조각이 6개가 아니면 false 를 반환하므로, 어떤 비밀번호도
통과할 수 없었다. 코드는 정확히 설계대로 동작했다 — 입력이 이미 망가져 있었다.

**진단이 늦어진 이유:** 형식 검사를 `process.loadEnvFile()` 로 했는데
**Node 내장 로더는 변수 확장을 하지 않는다.** 그래서 "형식 정상"이 나왔다.
검증 도구가 실제 소비자와 다른 경로로 값을 읽으면 그 검증은 아무것도
보장하지 않는다.

**따옴표로 감싸는 해법을 버린 이유:** `.env.local` 에서는 작은따옴표가
확장을 막지만, **버셀 대시보드는 따옴표를 값의 일부로 저장한다.** 로컬에서
고치면 배포에서 깨지고, 그 반대도 마찬가지다. 어디에 넣어도 안전한 값이어야 한다.

**해법:** 구분자를 `.` 으로 바꿨다. base64url 알파벳(`A-Za-z0-9_-`)과 겹치지
않고, 셸·dotenv·버셀 어디에서도 특별한 뜻이 없다. 기존 해시는 salt 와 hash 가
그대로이므로 구분자만 치환하면 되고, 비밀번호를 다시 정할 필요가 없었다.

**재발 방지:**

- `tests/auth/password.test.ts` 가 해시에 `$` 가 없는지, 그리고 전체가
  `[A-Za-z0-9._-]` 안에 드는지 검사한다
- `isHashFormatValid()` 를 만들어 로그인 라우트가 **"설정이 깨졌다"와
  "비밀번호가 틀렸다"를 서버 로그에서 구분**한다. 응답은 둘 다 401 그대로다 —
  설정 상태를 밖에 알려줄 이유가 없다. 이게 있었으면 몇 분 만에 잡혔다

**교훈:** 환경변수로 실어 나를 값은 그 통로가 값을 변형하지 않는지 먼저 본다.
그리고 검증은 **실제 소비자와 같은 경로로** 읽어서 해야 한다.

## 2026-09-01 — 창 닫기는 즉시 파기가 아니라 30초 유예다

**증상:** 대시보드에서 새로고침하면 로그아웃됐다. `sessions` 의 모든 행이
`revoked` 였다.

**원인:** `pagehide` 에서 `sendBeacon('/api/session/end')` 로 세션을 즉시
파기하고 있었다. **`pagehide` 는 창을 닫을 때만 발생하지 않는다** —
새로고침, 주소창 이동, 전체 페이지 내비게이션에서 똑같이 발생한다.
브라우저는 이 둘을 구분해서 알려주지 않는다.

스펙에 "브라우저 닫힘은 서버가 감지할 수 없다"고 써놓고도 beacon 을
즉시 파기에 연결한 것이 모순이었다. 감지할 수 없다면 그 신호로
되돌릴 수 없는 일을 하면 안 된다.

**해법:** beacon 이 파기 대신 **유휴 만료를 30초로 당긴다.**
전용 라우트 `POST /api/session/leaving` 이 이 일만 한다.

| | 창을 닫으면 | 새로고침하면 |
|---|---|---|
| 이전 | 즉시 파기 | **로그아웃** ← 버그 |
| 지금 | 30초 뒤 파기 | 살아남음 (첫 요청이 15분으로 되돌림) |

`[종료]` 버튼은 그대로 즉시 파기다 (`POST /api/session/end`).
사용자가 버튼을 누른 것은 의도가 분명하므로 되돌릴 수 없는 일을 해도 된다.

**당기기만 하고 늘리지 않는다.** `expireSoon` 의 WHERE 에
`idleExpiresAt > soon` 이 있다. 이게 없으면 만료 10초 전에 도착한 beacon 이
오히려 30초로 되돌려 세션을 연장해 준다 — **종료 신호가 연장 신호가 된다.**
가드를 빼고 테스트가 그 한 건만 정확히 깨지는 것을 확인했다.

`leaving` 은 쿠키를 지우지 않는다. 지우면 새로고침한 페이지가 세션을 잃는다.

**교훈:** 구분할 수 없는 두 사건을 하나의 신호로 받는다면, 그 신호로는
**되돌릴 수 있는 일만** 한다. 유예는 되돌릴 수 있고 파기는 되돌릴 수 없다.

## 2026-09-01 — ④겹은 선불 잔액이지 spend limit 이 아니다

OpenAI 대시보드에 하드 리밋을 걸면서, 어느 설정이 실제 상한인지 확인했다.

**Organization spend limit 은 최선 노력이다.** 설정 화면이 직접
"Your actual costs may exceed this based on usage" 라고 적어놓는다.
사용량 집계에 지연이 있어 초과분이 새어 나갈 수 있다.

**진짜 하드 스톱은 선불 잔액 + 자동 충전 OFF 다.** 잔액이 0 이 되면 API 가
에러를 반환하고 거기서 끝난다. 설정 실수로 뚫릴 여지가 없다.

**자동 충전은 결제 설정에서 기본값이 켜짐이다.** 켜져 있으면 잔액이 임계값
아래로 떨어질 때마다 카드에서 자동으로 크레딧을 산다 — 폭주 루프가 나면
태우고, 사고, 또 태운다. **이 프로젝트에서 되돌릴 수 없는 유일한 설정 실수다.**

**Tier 의 내장 한도는 방어가 아니다.** Tier 1 은 $5 결제로 자동 도달하고
내장 월 한도가 $100 이다 — 우리 예산의 5배, 코드 캡의 33배다.
등급을 상한으로 착각하면 안 된다.

최종 구성: 선불 $5 (자동 충전 OFF) / spend limit $5 / 알림 $3.50·$4·$5.
$3.50 알림이 울리는 것은 코드의 월 캡($3)이 실패했다는 뜻이다.

**왜 코드 밖에 한 겹이 필요한가:** 앞의 세 겹은 전부 내 코드가 지킨다.
1주차 마지막 날 손으로 돌려보는 것만으로 버그 셋이 나왔고, 그중 하나는
무한 루프로 한 라우트를 586번 호출했다. 그게 LLM 라우트였다면
③겹이 막았겠지만, ③겹에도 버그가 있었다면 ④겹만 남는다.

## 2026-09-01 — 스펙에 적힌 모델명을 그대로 믿지 않는다

대시보드의 「Models in use」에 `gpt-5.5` / `gpt-5.5-pro` / `gpt-5.4-mini` 가
떴다. 스펙과 계획은 `gpt-4o-mini` 로 못박혀 있다. 라인업이 바뀌었다.

2주차 첫 작업이 `lib/llm/client.ts` 이고 거기서 모델 ID 와 단가가 정해진다.
`monthlyCostCapMicros()` 의 $3 캡도 옛 단가 위에서 계산한 값이다.

**2주차 계획을 쓸 때 실제 모델 목록과 가격을 확인해 확정한다.**
추측으로 모델명을 적지 않는다 — 이 프로젝트에서 이미 두 번 대가를 치렀다
(Next 16 의 `params` 와 `runtime` export, zod 4 의 이슈 코드).

**확인 결과 (같은 날, 위 항목의 후속):** 걱정은 근거가 없었다.
`gpt-4o-mini` 는 deprecation 목록에 없고, Structured Outputs 를 지원하며
(컨텍스트 128k, 최대 출력 16,384), 대시보드의 「Models in use」는 인기 모델을
보여준 것이지 사용 가능 목록이 아니었다. **스펙을 바꾸지 않는다.**

가격을 보면 바꾸면 안 되는 이유가 분명하다 (per 1M):

| 모델 | 입력 | 출력 |
|---|---|---|
| **gpt-4o-mini** | **$0.15** | **$0.60** |
| gpt-5.4-mini | $0.75 | $4.50 |
| gpt-5.5 | $5.00 | $30.00 |

지문 2000토큰 생성이 주 작업이라 **출력 단가가 지배한다 — 7.5배 차이다.**

최대 사용(3과목 × 매일 × 재시도 전부 소진 = 하루 15호출) 기준 월 추정:
입력 603K, 출력 432K → **월 $0.35.** 예산 3만원(≈$20)의 1.7% 이고
코드 캡 $3 의 1/8.5 다. gpt-5.4-mini 였다면 같은 사용량에 $2.39 로
캡에 거의 닿는다.

**남은 것:** 위 계산은 내 토큰 추정치다. 며칠 돌리면 `usage_ledger` 에
실측이 쌓이므로 2주차 후반에 캡을 다시 잡는다. 지금 조이면 추정이
틀렸을 때 멀쩡한 요청이 429 로 막힌다.
