## 2026-08-31 — 별도 백엔드(Express/FastAPI)를 두지 않는다

Next.js Route Handler가 백엔드 역할을 전부 한다.

버셀 배포가 전제인데 백엔드를 분리하면 배포 대상 2개, CORS, 쿠키 도메인,
환경변수 2벌, 로컬 프로세스 2개가 따라붙는다. 1인용 앱에서 이는 순수 비용이다.
Route Handler로도 API 키는 서버에만 남으므로 보안 목표는 동일하게 달성된다.

**되돌리려면:** 라우트 핸들러의 로직이 이미 `lib/` 아래 순수 함수로 분리돼 있으므로
FastAPI/Express로 옮기는 것은 어댑터 작성 수준이다.

## 2026-08-31 — Redis 대신 Postgres 단일

TTL 자동 만료는 `expires_at` 컬럼 + 조회 시 비교로, 원자적 카운터는
`UPDATE ... SET n = n + 1 RETURNING n`으로 Postgres에서 동등하게 구현된다.
저지연은 사용자 1명에게 의미가 없다. 계정·환경변수·장애지점을 하나 줄이는 이득이 더 크다.

**되돌리려면:** `SessionStore` 인터페이스에 `RedisSessionStore` 구현체를 추가한다.
라우트 코드는 바뀌지 않는다.

## 2026-08-31 — 세션이 아니라 예산 카운터가 진짜 방어선

원래 요구사항은 "세션 종료 시 API 원천 차단"이었다.
하지만 세션이 살아있는 15분 동안은 호출이 무제한이므로, 프론트의 `useEffect`
의존성 실수 하나로 인증된 세션이 초당 수십 번 호출을 낸다.
**세션은 "누가"를 막지 "얼마나"를 막지 않는다.**

그래서 방어를 4겹으로 나눴다 — 세션 게이트 / DB UNIQUE 멱등성 / 예산 카운터 /
OpenAI 계정 하드 리밋. 이 중 비용의 대부분을 잡는 것은 **멱등성 제약**이다.

## 2026-08-31 — "당일 추가 생성 없음"을 DB 제약으로 구현

프론트 규칙이나 서비스 계층 검사가 아니라 `study_days`의
`UNIQUE (subject, day_no)` + `UNIQUE (subject, study_date)` 두 제약으로 강제한다.

프론트 규칙은 버그로 뚫린다. DB 제약은 안 뚫린다.
새로고침을 100번 해도 LLM 호출은 정확히 1회다.

## 2026-08-31 — 하트비트 ping을 넣지 않는다

세션 생존을 알리는 주기적 ping은 흔한 패턴이지만 여기서는 **기능을 정확히 무력화한다.**
탭이 열려 있는 한 유휴 타임아웃이 영원히 갱신되어 "자리 비움 차단"이 사라진다.

`idle_expires_at`은 실제 학습 행동(콘텐츠 요청, 답안 제출, 정리본 저장)에만 밀린다.
대신 클라이언트에 남은 시간 카운트다운을 표시하고 만료 2분 전 배너를 띄운다.

## 2026-08-31 — Next 16 이 계획과 다른 지점 두 곳

뼈대를 세우고 `node_modules/next/dist/docs/` 를 읽어 확인한 것.

1. **`export const runtime = 'nodejs'` 를 쓰지 않는다.** Next 16 에서 nodejs 가 기본값이고
   Edge 런타임은 deprecated 다. 문서가 이 export 의 제거를 명시적으로 권한다.
2. **동적 라우트의 `params` 는 Promise 이며 두 번째 인자(context)로 온다.**
   따라서 `withSession` 가드가 context 를 핸들러까지 그대로 넘겨야 한다.
   원래 계획은 `new URL(req.url).pathname.split('/')[3]` 로 세그먼트를 잘라 쓰려 했는데,
   경로 구조가 바뀌면 조용히 깨지는 방식이었다.

**교훈:** 프레임워크 메이저 버전이 학습 데이터보다 새로우면 추측하지 말고
`node_modules/<pkg>/dist/docs/` 를 먼저 읽는다. 이 규칙을 `CLAUDE.md` 에 넣었다.

## 2026-08-31 — 비밀 검사를 부정 목록이 아니라 허용 목록으로

`check:secrets` 를 "모든 파일에서 NEXT_PUBLIC_ 금지"로 짰더니 **검사기 자신의 테스트 파일을

## 2026-08-31 — argon2id 대신 node:crypto 의 scrypt

스펙 §3.5는 argon2id를 명시했으나 구현 단계에서 scrypt로 바꿨다.

argon2 npm 패키지들은 네이티브 모듈(NAPI)이라 버셀 서버리스 번들링에서 깨질 위험이 있다.
`node:crypto` 의 `scrypt` 는 표준 라이브러리이고 메모리 하드 KDF 로서
비밀번호 하나를 지키기에 충분하다. 의존성 0개, 배포 위험 0개.

저장 형식에 파라미터를 함께 넣었다(`scrypt$N$r$p$salt$hash`)므로
나중에 비용을 올려도 기존 해시를 계속 검증할 수 있다.

`verifyPassword` 는 확신할 수 없는 모든 경우에 false 를 준다.
특히 `AUTH_PASSWORD_HASH` 가 비어 있을 때 반드시 false 여야 한다 —
여기서 true 가 나오면 인증이 통째로 무력화된다. 이 경우를 테스트로 못박았다.

**되돌리려면:** `lib/auth/password.ts` 두 함수만 교체한다. 호출부는 바뀌지 않는다.

## 2026-08-31 — DB 연결을 지연시킨다

`lib/db/client.ts` 를 모듈 최상위에서 `DATABASE_URL` 을 검사하고 던지도록 짰다.
"런타임에 조용히 실패하는 것보다 빌드에서 큰 소리로 깨지는 게 낫다"는 판단이었는데
**틀렸다.**

Next 빌드는 라우트 모듈을 import 해서 설정을 수집한다. 그래서 첫 라우트를 추가한
순간 `npm run build` 가 깨졌다 — DB URL 없이는 빌드도, CI 도, 타입 검사도 못 돈다.

Proxy 로 감싸 첫 사용 시점에 연결하게 바꿨다. import 는 항상 성공하고,
실제로 쿼리를 날릴 때 같은 메시지로 실패한다. 두 경우 다 테스트로 못박았다.

**교훈:** "빌드에서 깨지는 게 낫다"는 빌드가 그 코드를 실행하지 않을 때만 맞는 말이다.

## 2026-09-01 — 비밀번호 해시 구분자를 `$` 에서 `.` 으로

**증상:** 맞는 비밀번호를 넣어도 전부 거부됐다. 로그인 화면은 "비밀번호가
틀렸다"만 보여줬다.

**원인:** Next 의 dotenv 로더는 **변수 확장을 한다.** 해시 형식이
`scrypt$16384$8$1$salt$hash` 였는데, `$16384` · `$8` · `$1` · `$salt…` 를
전부 환경변수 참조로 보고 빈 문자열로 치환했다.

```
파일에 적힌 값    : 조각 6개, 길이 83
앱이 읽은 값      : 조각 1개, 길이 25   "scrypt6384-bda_kLQQrOKzgA"
```

`verifyPassword` 는 조각이 6개가 아니면 false 를 반환하므로, 어떤 비밀번호도
통과할 수 없었다. 코드는 정확히 설계대로 동작했다 — 입력이 이미 망가져 있었다.

**진단이 늦어진 이유:** 형식 검사를 `process.loadEnvFile()` 로 했는데
**Node 내장 로더는 변수 확장을 하지 않는다.** 그래서 "형식 정상"이 나왔다.
검증 도구가 실제 소비자와 다른 경로로 값을 읽으면 그 검증은 아무것도
보장하지 않는다.

**따옴표로 감싸는 해법을 버린 이유:** `.env.local` 에서는 작은따옴표가
확장을 막지만, **버셀 대시보드는 따옴표를 값의 일부로 저장한다.** 로컬에서
고치면 배포에서 깨지고, 그 반대도 마찬가지다. 어디에 넣어도 안전한 값이어야 한다.

**해법:** 구분자를 `.` 으로 바꿨다. base64url 알파벳(`A-Za-z0-9_-`)과 겹치지
않고, 셸·dotenv·버셀 어디에서도 특별한 뜻이 없다. 기존 해시는 salt 와 hash 가
그대로이므로 구분자만 치환하면 되고, 비밀번호를 다시 정할 필요가 없었다.

**재발 방지:**

- `tests/auth/password.test.ts` 가 해시에 `$` 가 없는지, 그리고 전체가
  `[A-Za-z0-9._-]` 안에 드는지 검사한다
- `isHashFormatValid()` 를 만들어 로그인 라우트가 **"설정이 깨졌다"와
  "비밀번호가 틀렸다"를 서버 로그에서 구분**한다. 응답은 둘 다 401 그대로다 —
  설정 상태를 밖에 알려줄 이유가 없다. 이게 있었으면 몇 분 만에 잡혔다

**교훈:** 환경변수로 실어 나를 값은 그 통로가 값을 변형하지 않는지 먼저 본다.
그리고 검증은 **실제 소비자와 같은 경로로** 읽어서 해야 한다.

## 2026-09-01 — 창 닫기는 즉시 파기가 아니라 30초 유예다

**증상:** 대시보드에서 새로고침하면 로그아웃됐다. `sessions` 의 모든 행이
`revoked` 였다.

**원인:** `pagehide` 에서 `sendBeacon('/api/session/end')` 로 세션을 즉시
파기하고 있었다. **`pagehide` 는 창을 닫을 때만 발생하지 않는다** —
새로고침, 주소창 이동, 전체 페이지 내비게이션에서 똑같이 발생한다.
브라우저는 이 둘을 구분해서 알려주지 않는다.

스펙에 "브라우저 닫힘은 서버가 감지할 수 없다"고 써놓고도 beacon 을
즉시 파기에 연결한 것이 모순이었다. 감지할 수 없다면 그 신호로
되돌릴 수 없는 일을 하면 안 된다.

**해법:** beacon 이 파기 대신 **유휴 만료를 30초로 당긴다.**
전용 라우트 `POST /api/session/leaving` 이 이 일만 한다.

| | 창을 닫으면 | 새로고침하면 |
|---|---|---|
| 이전 | 즉시 파기 | **로그아웃** ← 버그 |
| 지금 | 30초 뒤 파기 | 살아남음 (첫 요청이 15분으로 되돌림) |

`[종료]` 버튼은 그대로 즉시 파기다 (`POST /api/session/end`).
사용자가 버튼을 누른 것은 의도가 분명하므로 되돌릴 수 없는 일을 해도 된다.

**당기기만 하고 늘리지 않는다.** `expireSoon` 의 WHERE 에
`idleExpiresAt > soon` 이 있다. 이게 없으면 만료 10초 전에 도착한 beacon 이
오히려 30초로 되돌려 세션을 연장해 준다 — **종료 신호가 연장 신호가 된다.**
가드를 빼고 테스트가 그 한 건만 정확히 깨지는 것을 확인했다.

`leaving` 은 쿠키를 지우지 않는다. 지우면 새로고침한 페이지가 세션을 잃는다.

**교훈:** 구분할 수 없는 두 사건을 하나의 신호로 받는다면, 그 신호로는
**되돌릴 수 있는 일만** 한다. 유예는 되돌릴 수 있고 파기는 되돌릴 수 없다.

## 2026-09-01 — ④겹은 선불 잔액이지 spend limit 이 아니다

OpenAI 대시보드에 하드 리밋을 걸면서, 어느 설정이 실제 상한인지 확인했다.

**Organization spend limit 은 최선 노력이다.** 설정 화면이 직접
"Your actual costs may exceed this based on usage" 라고 적어놓는다.
사용량 집계에 지연이 있어 초과분이 새어 나갈 수 있다.

**진짜 하드 스톱은 선불 잔액 + 자동 충전 OFF 다.** 잔액이 0 이 되면 API 가
에러를 반환하고 거기서 끝난다. 설정 실수로 뚫릴 여지가 없다.

**자동 충전은 결제 설정에서 기본값이 켜짐이다.** 켜져 있으면 잔액이 임계값
아래로 떨어질 때마다 카드에서 자동으로 크레딧을 산다 — 폭주 루프가 나면
태우고, 사고, 또 태운다. **이 프로젝트에서 되돌릴 수 없는 유일한 설정 실수다.**

**Tier 의 내장 한도는 방어가 아니다.** Tier 1 은 $5 결제로 자동 도달하고
내장 월 한도가 $100 이다 — 우리 예산의 5배, 코드 캡의 33배다.
등급을 상한으로 착각하면 안 된다.

최종 구성: 선불 $5 (자동 충전 OFF) / spend limit $5 / 알림 $3.50·$4·$5.
$3.50 알림이 울리는 것은 코드의 월 캡($3)이 실패했다는 뜻이다.

**왜 코드 밖에 한 겹이 필요한가:** 앞의 세 겹은 전부 내 코드가 지킨다.
1주차 마지막 날 손으로 돌려보는 것만으로 버그 셋이 나왔고, 그중 하나는
무한 루프로 한 라우트를 586번 호출했다. 그게 LLM 라우트였다면
③겹이 막았겠지만, ③겹에도 버그가 있었다면 ④겹만 남는다.

### 결함 ① — 지문이 문제의 답을 그대로 담았다

프롬프트는 **"지문 안에 문제의 답을 그대로 노출하지 마라"** 고 명시한다.
그런데 지문 3문단이 "웹 브라우저 탭 전환" 예시를 상세히 설명했고,
q3(application)이 정확히 그것을 물었다:

> q3: 웹 브라우저에서 여러 탭을 사용할 때 컨텍스트 스위칭이 어떻게
> 발생하는지 구체적인 예를 들어 설명하시오.

**답이 지문에 그대로 있다.** application 문제가 적용을 시험하지 못한다.
모델이 지문의 예시를 그대로 문제로 재활용한 것이다.

원인 추정: 프롬프트가 "예시를 반드시 하나 이상 넣는다"와 "답을 노출하지
마라"를 동시에 요구하는데, 모델이 그 둘의 긴장을 풀지 못했다.
**한 번의 표본으로 단정하지 않는다** — 여러 Day 를 만들어보고 반복되면
프롬프트를 고친다 (application 문제는 지문에 없는 상황을 쓰라고 명시).

### 결함 ② — 어투가 앱과 어긋난다

지문이 "~습니다" 체다. 앱의 나머지 전부(UI 문구, 채점 피드백 지시)는
평서체 "~다" 다. 시스템 프롬프트가 어투를 지정하지 않았다.

이건 프롬프트 한 줄로 고칠 수 있고 논란의 여지가 없다.

### 결함 ③ — 루브릭에 주관이 섞였다

프롬프트는 "판정 불가능한 표현 금지"를 명시하는데, 나온 루브릭에
**"정확하게 컨텍스트 스위칭의 개념을 정의했음"** 이 있다. "정확하게"가
판정자의 주관이다. 나머지("PCB의 역할에 대해 언급했음")는 검증 가능하다.

또 루브릭이 "답안이 X 했음" 형태로 나왔다. 스펙의 의도는 "답안에 X 라는
내용이 있어야 한다" 쪽에 가깝다. 채점 프롬프트가 이 형태로도 대조는
하겠지만, 표현이 기준이 아니라 판정처럼 읽힌다.

**세 결함 모두 지금 고치지 않는다.** 표본이 하나뿐이고, 고칠 때마다
호출이 필요하며 오늘 일일 캡은 3회다. Task 12 에서 여러 Day 를 만들어본
뒤 반복되는 것만 고친다. 프롬프트를 표본 하나로 흔들면 다음 표본에서
다른 문제가 나온다.

## 2026-09-01 — 모델이 준 점수를 화면에 쓰지 않는다

첫 실제 채점을 돌렸다. 답안을 일부러 세 가지 성격으로 넣었다 —
충실한 답 / 일부러 얇은 답 / 지문과 완전히 다른 표현으로 쓴 답.

**채점 자체는 잘 했다:**

| | 판정 | 비고 |
|---|---|---|
| q1 충실한 답 | 3 / 3 | 정확 |
| q2 얇은 답 | 0 / 3 | 놓친 셋을 정확히 짚음 |
| q3 다른 표현 | 3 / 3 | **용어를 하나도 안 썼는데 의미로 맞다고 봄** |

q3 가 핵심이다. "탭" 대신 "창", "프로세스" 대신 "실행 단위"로 썼는데도
통과했다 — 프롬프트의 "표현이 달라도 의미가 같으면 맞은 것으로 본다"가
실제로 작동한다. 다만 관대한 쪽으로 기운 것도 사실이다.

**그런데 점수 계산식을 지키지 않았다.**

프롬프트는 "(맞은 포인트 수 / 전체 포인트 수) × 100 을 반올림한 값이다.
임의로 조정하지 마라"고 명시한다. q2 는 3개를 **전부 놓쳤는데 50점**이
나왔다. 0 이어야 한다.

| | 포인트 | 모델 점수 | 계산식대로면 |
|---|---|---|---|
| q2 | 0 / 3 | **50** | **0** |
| 전체 | 6 / 9 | 83 | 67 |

**해법: `score` 필드를 화면에 쓰지 않는다.** `GradeResult` 가
`correct_points.length / (correct + missed).length` 를 직접 센다.
그래서 화면에는 `6 / 9` 가 뜬다.

이건 프롬프트로 고칠 문제가 아니다. **숫자를 계산하는 일은 모델에게
맡기지 않는다** — 근거(맞은/놓친 포인트)는 모델이 주고, 그걸로 점수를
만드는 것은 우리가 한다. 그러면 화면과 루브릭이 항상 일치한다.

`score` 필드는 스키마에 남겨둔다. 지우면 Structured Outputs 스키마를
바꿔야 하고, 모델이 그 칸을 채우면서 판정을 정리하는 효과도 있을 수 있다.
다만 **읽지 않는다.**

## 2026-09-01 — 한국어는 `word-break: keep-all` 이 필요하다

시작 화면의 안내 문구가 **"다시 만들 수 없 / 고,"** 로 끊겼다.
음절 중간에서 줄이 바뀐 것이다.

브라우저 기본값(`word-break: normal`)은 한국어를 음절 단위로 쪼갤 수 있다.
`text-balance` 는 줄 길이만 고르게 맞출 뿐 어절을 지켜주지 않는다.
`body` 에 `word-break: keep-all` 을 넣어 어절 단위로만 끊게 했다.

가운데 정렬에서 특히 눈에 띈다 — 양쪽 끝이 모두 들쭉날쭉한 상태에서
음절까지 잘리면 읽는 리듬이 두 번 깨진다.

**교훈:** 한국어 UI 의 줄바꿈은 기본값이 틀렸다고 보고 시작한다.

## 2026-09-01 — 기한 당일의 복습은 "0일 밀림"이 아니다

`priorityOf` 의 첫 항이 `120 × min(7, overdueDays)` 였다. 주석은

밀리고, 하루 밀린 뒤에야 120점을 받는다. 간격 반복이 통째로 하루씩
늦게 도는 셈이라 예약이 의미를 잃는다.

인자를 `dueDays` 로 바꿨다 — **"며칠째 기한인가"이지 "며칠 밀렸나"가
아니다.** 오늘이 기한이면 1이다.

**대가가 있다.** 복습이 슬롯을 더 가져가므로 신규 진도가 느려진다.

## 2026-09-02 — 채점 결과를 루브릭에 맞춰 다시 센다

실호출로 하루를 완주하다 잡았다. 채점 포인트가 2개인 문제에서
gpt-4o-mini 가 「동사는 "ran"이다」를 `correct_points` 와 `missed_points`
**양쪽에** 넣어 3개로 만들었다. 학습자는 동사를 `quickly` 라고 틀리게

프롬프트에 "두 배열의 합은 채점 포인트 개수와 같아야 한다"고 적어뒀지만
지키지 않았다. **모델의 산술을 안 믿기로 한 것과 같은 이유로, 모델이
만든 집합도 믿지 않는다.**

`reconcilePoints` 가 저장된 루브릭을 기준으로 다시 센다:

- 루브릭에 없는 포인트는 버린다 (모델이 지어낸 것)
- 양쪽에 다 있으면 **놓친 것**으로 본다 (다투는 포인트에 점수를 주지 않는다)
- 언급되지 않은 포인트는 놓친 것이다
- 모델이 통째로 빠뜨린 문제는 그 루브릭 전부가 놓친 것이다

그래서 맞음 + 놓침은 **언제나 루브릭 개수와 같다.** 정리된 결과를
저장하므로 화면에 보이는 것과 점수의 근거가 어긋날 수 없다.

모델이 하는 일은 "이 답이 이 포인트를 담았는가" 판정뿐이다.
세는 일은 전부 우리가 한다.

## 2026-09-02 — 못 넘긴 Topic 의 회복 정책 (사용자 결정)

사용자가 정했다:

> "복습 기회는 1번 정도 주고, 만약 복습할 때도 틀리면 그 하위 개념으로
> 공부하고, 하위 개념 통과 시 다시 복습 진행 후, 맞든 틀리든 다음 학습
> 진도로 진행"

`lib/mastery/recovery.ts` 의 `recoveryPhaseOf` 가 이 문장 그대로다.

| `attempt_count` | 단계 | 오늘 무엇을 하나 |
|---|---|---|
| 0–1 | `retry` | 원래 지문을 다시 읽는다 (**생성 0회**) |
| 2, 못 넘긴 하위 있음 | `remediation` | 하위 개념 하나. **본인은 안 한다** |
| 2, 하위 다 넘김 | `final-retry` | 마지막으로 한 번 |
| 2, 내려갈 하위 없음 | `parked` | 접어둔다 |
| 3 이상 | `parked` | 접어둔다 |

**단계를 `attempt_count` 에서 유도한다.** 별도의 상태 칼럼을 만들지 않았다 —
같은 사실을 두 곳에 두면 어긋났을 때 진실을 정할 수 없다 (1주차의 결정을 계승).

### 왜 필요했나

우선순위의 `80 × min(5, wrongCount)` 는 최대 400점이라 다른 모든 항을
압도한다. 게다가 취약 재학습은 콘텐츠를 새로 안 만들어 `fitToBudget` 이
자르지도 못한다. 그래서 한 과목이 막히면 30일이 그 과목 재시도로 채워졌다.

30일 시뮬레이션 (수학만 계속 틀리는 학습자):

| | 전 | 후 |
|---|---|---|
| 복습 슬롯 | 120 | 71 |
| 신규 슬롯 | 9 | 26 |
| 건드린 Topic | 9 | 27 |
| 영어 숙달 | 2 | 10 |

### 같이 고친 것 셋

**1. 취약 Topic 이 "복습 회차"로 잡히던 것.**
①(기한 복습)이 ②(취약)보다 먼저 돌고 `push` 가 topicId 로 중복을 막는다.
실패하면 `resetSchedule` 이 복습을 내일로 잡으므로, 취약 Topic 이 ① 에
먼저 걸려 `round: 1` 짜리 복습이 됐다 — **콘텐츠 생성 비용이 붙었다.**
「취약은 원래 지문을 다시 읽고 생성이 0회」라는 기존 결정과 정반대였다.
① 이 `status === 'weak'` 를 건너뛴다.

**2. 접어두기가 보충 경로로 무력화되던 것.**
부모가 취약인 한 매일 같은 하위 개념을 요구하므로, 접어둔 하위가 부모의
보충으로 계속 끌려나왔다. 하위의 자기 단계도 확인한다.

**3. 접어둔 것이 영영 안 돌아오던 것.**
못 넘긴 Topic 이 core 선수면 그 아래 가지가 통째로 잠긴다.
`PARK_DAYS = 14` 뒤에 한 바퀴 다시 준다 — 간격 반복의 마지막 간격과 같다.
**"다음 진도로 진행"은 지금 비켜준다는 뜻이지 영영 포기한다는 뜻이 아니다.**

### 마지막 안전망

전부 못 넘겨 새 Topic 이 하나도 안 열리면 하루가 빌 수 있다. 그럴 때만
가장 오래 안 본 것을 하나 되살린다 (재학습이라 생성 0회). 접어두기의
취지는 **다음 진도가 있을 때** 비켜주는 것이지 할 일을 없애는 것이 아니다.

## 2026-09-02 — 생성물의 문체를 평서체로 못박는다

실호출 표본 3개가 **전부** 존댓말("~합니다")로 나왔다. 앱의 다른 모든 문장은
평서체("~다")라서, 지문만 존댓말이면 한 화면 안에서 목소리가 둘이 된다.

`VOICE_RULE` 을 만들어 콘텐츠·복습·채점 세 프롬프트가 공유한다.

**"평서체로 써라"만 적지 않았다.** 모델은 한국어에서 존댓말로 기우므로
금지할 어미를 하나하나 적고("~합니다", "~입니다", "~하세요", "~해요")
고쳐 쓴 예시까지 붙였다. 문제 지시도 "~하시오"가 실제로 나왔으므로
"~하라"로 못박았다.

테스트가 지키는 것은 **프롬프트가 문체를 말하는가**까지다. 모델이 실제로
지키는지는 실호출로만 안다 — 테스트에서 LLM 을 부르지 않기 때문이다.
2026-09-03 에 예약된 복습 생성이 첫 확인이다.

프롬프트 자신도 평서체로 쓰여 있는지 테스트가 확인한다. 시키는 문체와
다른 문체로 지시하면 모델이 지시가 아니라 예시를 따라간다.

**이미 만들어진 자료는 `topic_contents` UNIQUE 때문에 다시 안 만들어진다.**
이 규칙의 효과는 다음 Topic 부터다 — 그래서 미루지 않고 먼저 했다.

## 2026-09-02 — Topic 상세 화면은 "왜"에 답한다

계획 화면은 한 줄로만 말한다 — 「복습 1회차 · 0일 밀림」, 「이해가 부족했다」.
근거를 보려면 DB 를 열어야 했다.

`/topic/[topicId]` 가 세 가지 "왜"에 답한다.

- **왜 아직 안 열렸나** — 못 넘긴 선수와 각자의 점수/기준.
  과목을 넘는 선수는 색으로 구분한다. 진도가 막힌 이유가 대개 거기다
- **왜 오늘 또 나왔나 · 왜 안 나오나** — 회복 단계를 사람 말로 옮긴다.
  "세 번 했는데 못 넘겼다. 지금은 접어두고 14일 뒤에 다시 온다"
- **왜 이걸 배우나** — `_links.yaml` 의 과목 간 연결

`hasMaterial` 도 적는다 — "자료가 이미 있다 · 다시 열어도 AI 호출 0회".
돈이 드는지 아닌지는 누르기 전에 알아야 한다.

### 조사를 "을(를)"로 도망가지 않는다

## 2026-09-02 — `/admin/usage` — 비용을 화면으로 꺼낸다

지금까지 비용은 `scripts/peek.mjs` 로만 볼 수 있었다. **터미널에서만 보이는

`usage_ledger` 를 다시 더해서 보여주면 화면과 캡 판정이 어긋날 수 있다.
롤백된 예약이나 기록 누락이 생기면 **화면은 안전하다고 말하는데 실제로는

보여준다. 원장 합계는 「누적」으로 따로 둔다 — 둘은 다른 질문이다.

### 캡에 닿기 전에 말한다

`daysUntilCap` — 지금 속도로 며칠이면 이번 달 예산이 차는가. 다 쓰고 429 를

`null` 이다** — 없는 위험을 만들지 않는다.

### 금액 표기의 자릿수를 금액에 맞춘다

한 번 호출이 $0.000559 다. 소수 둘째 자리로 자르면 화면이 전부 `$0.00` 이

두 자리다.

### 날짜별 묶기를 SQL 이 아니라 코드에서 한다

`created_at` 은 timestamptz 이고 서버는 UTC 로 돈다. `date_trunc` 로 묶으면
한국 시간 오전 9시 이전 호출이 전날로 간다. 원장을 통째로 읽어 `kstToday`
하나로 묶는다 — 날짜를 만드는 곳을 늘리지 않는다.

원장을 통째로 읽는 것은 크기 때문에 가능하다. 하루 캡이 20회라 1년을 써도
7천 행 남짓이다. 합계를 SQL 로 나눠 내면 같은 정의가 두 곳에 생긴다.

### 「다시 써서 아낀 것」은 추정이라고 말한다

멱등성 ②겹이 실제로 막은 돈이다. 자료 하나의 평균 생성비를 다시 쓴 횟수에
곱한다. 실제로 다시 만들었다면 프롬프트가 달라 값도 달랐을 것이므로
**정확한 금액이 아니라 규모다.** 화면에도 그렇게 적었다.

### 마지막 방어선이 화면 밖에 있다는 것을 화면에 적는다

이 숫자는 앱이 센 것이다. ④겹(OpenAI 대시보드 하드 리밋 · 자동 충전 OFF)은
코드가 못 막는다. 화면 아래에 그 문장을 두어 **이 화면만 보고 안심하지
않도록** 했다.

## 2026-09-02 — 캡은 행이 아니라 환경에서 온다 (배포 첫날 발견)

`reserve()` 가 카운터 행을 처음 만들 때 그 시점 환경의 캡을 **행에 굳혀
넣고**, 이후 `onConflictDoNothing` 이라 다시는 안 고쳐졌다. WHERE 절도
행의 `cap_calls`/`cap_micros` 와 비교했다.

**배포하고 나서 실제로 이렇게 됐다:**

```
day:2026-09-02   calls 2   cap_calls 3        ← 로컬이 만든 행
month:2026-09    calls 3   cap_micros 500000  ← $0.50
```

`APP_ENV=production` 을 넣고 배포했는데도 배포된 앱이 **그날은 3회, 그 달은
$0.50** 에 묶여 있었다. 로컬에서 하루 열어보고 배포하면 항상 이렇게 된다.

**캡을 정하는 것은 환경이다. 행은 세기만 한다.** WHERE 절이 환경 값과
비교하고, 행의 cap 컬럼은 「마지막으로 예약한 환경이 무엇이었나」를 남기는
기록으로만 쓴다. `loadUsage` 도 환경에서 읽는다 — **막히는 지점과 화면이
같은 곳을 봐야 한다.**

완화 쪽으로만 움직이지 않는다는 것도 테스트로 박았다. 환경 캡이 이미 쓴
횟수보다 낮아지면 그 즉시 막힌다.

성격마다 만들 것이 진짜로 다르다. 상수 하나로는 표현할 수 없다.

- **어휘** — 지문을 **영어**로 쓴다. 주어진 단어가 전부 등장하는 300~500단어

- **개념** — 지금까지의 레시피 그대로
- **문제 풀이** — 설명은 짧게, 문제가 본체

성격마다 레시피가 반드시 하나 있어야 한다. 없으면 조용히 엉뚱한 자료가

`forbidden` 은 아직 안 배운 후속 Topic 의 키워드를 막는다. 개념 Topic 에서


6개 중 5개가 `weak`. 원인은 **되먹임이 끊겨 있었다는 것**이다. 채점이 주는
것은 「놓침 — `'propose'`의 정의」 같은 **루브릭 조각**이지 설명이 아니고,
`retry` 복습은 **같은 지문을 다시 읽고 다시 답 쓰기**다. 그 사이에 새로
얻는 정보가 하나도 없다. 틀린 채로 다시 틀릴 수밖에 없는 구조였다.

### 해설은 자료에 싣는다 (채점이 아니라)

네 가지를 원했다 — 모범답안 · 풀이 단계 · 지문 근거 · 내 답의 어디가 왜.
**앞의 셋은 학습자 답과 무관하다.** 답에 따라 변하지 않는 것을 채점할
때마다 다시 만들 이유가 없다.

| | 자료에 싣기 | 채점에 싣기 |
|---|---|---|
| 호출 수 | 변화 없음 | 변화 없음 |
| 생성 횟수 | Topic 당 평생 1회 | 채점할 때마다 |
| 응답 크기 | Topic 마다 분산 | 3 Topic × 3문제 = 해설 9개를 한 응답에 |
| 잘릴 위험 | 낮다 | **높다 — 그리고 zod 실패는 롤백하지 않는다** |

마지막 줄이 결정적이다. 채점은 이미 이 앱에서 가장 큰 응답이고, 잘리면
**돈은 나갔는데 결과가 없다.** 거기를 두 배로 키우는 것이 가장 위험한
선택이었다.

개인화("내 답의 어디가 왜")는 새 필드를 만들지 않았다. `feedback_ko` 가
이미 자리를 갖고 있고 얕았을 뿐이라, 프롬프트에 한 줄을 더했다 —
**학습자가 쓴 문장을 직접 인용하라.** 「~가 빠졌다」로 끝나면 무엇을 고쳐야
할지 알 수 없다.

### 세 조각으로 나눠 받는다

마크다운 한 덩어리로 받으면 모델이 매번 다르게 구성해 화면이 일정하지 않고,
빠뜨려도 알 수 없다. `answer_md` · `steps` · `evidence` 로 나누면 화면이
각각을 다르게 그리고 zod 가 빠진 것을 잡는다.

`evidence` 를 「몇 번째 문단」이 아니라 **문장 그대로** 옮기게 한 이유는
지문이 한 덩어리 마크다운이라 위치 참조가 불안정해서다. 지문 밖에서
생각해야 하는 문제도 있으므로 빈 문자열을 허용한다 — 그건 테스트로 박았다.

### ★ `publicQuestions` 에 테스트가 하나도 없었다

루브릭·힌트가 학습 화면으로 새는 것을 막는 **유일한 장치**인데 아무도
지키지 않고 있었다. 모범답안이 들어오면서 막을 것이 하나 더 늘었다.

화이트리스트로 잠갔다 — 「`id`·`type`·`prompt` 말고는 아무것도 없다」.
앞으로 문제에 무슨 필드를 더하든 이 테스트가 먼저 깨진다.

`solutionsOf` 를 따로 만들고 `publicQuestions` 를 넓히지 않은 것도 같은
이유다. 그 함수의 이름은 「채점 전에 보여도 되는 것」이라는 뜻이고, 그 뜻이
흐려지면 다음 사람이 거기에 비밀을 하나 더 얹는다.

### 기존 자료 6개는 백필하지 않는다

접근을 고를 때 A 의 단점으로 「이미 만든 자료엔 해설이 없다」를 들었는데,
실제 데이터를 보니 필요 없었다. 6개 전부 복습 기한이 지났고(09-13·09-15)
다음에 열면 **복습 자료를 새로 만든다** — 새 문제, 새 해설. 보충으로 빠져도
하위 Topic 의 새 자료를 만든다.

먼저 넣고, 다음 학습에서 해설이 실제로 나오는지 본다. 그래도 아쉬우면 그때
백필한다. 스크립트를 미리 만드는 것은 YAGNI 다.

### 비용

콘텐츠 호출당 출력 +400토큰쯤 ≈ **+$0.00024**, Topic 당 평생 1회.
65개 전부 해도 +$0.016. **호출 수는 변하지 않는다** — 「하루 호출 = 생성이
필요한 항목 수 + 1」 그대로다.

`MAX_TOKENS_CONTENT` 2,500 → 3,200 · `MAX_TOKENS_REVIEW` 1,400 → 1,900.
실측 출력이 800~970이라 여유는 있었지만 해설 3개가 붙으면 상한에 닿는다.

## 2026-09-27 — 읽는 스키마와 생성 스키마는 같을 수 없다 (회귀)

해설(`solution`)을 **필수** 필드로 더한 직후, 사용자가 학습에 들어가니
이것만 떴다:

> 저장된 자료를 지금 형식으로 읽을 수 없다. 다시 만들지 않는다 — 이건 사람이 볼 일이다.

**그 전에 만들어진 자료 6개가 전부 무효가 됐다.** 학습이 통째로 막혔고,
그 경로는 일부러 자료를 다시 만들지 않으므로 **스스로 풀리지도 않는다.**

### 원인

`loadStoredMaterial` 이 **모델 응답을 검증하는 스키마로 저장된 행을 읽고
있었다.** 저장된 행은 옛날 코드가 쓴 것이다. 지금 스키마가 요구하는 필드가
거기 있을 이유가 없다.

바로 앞 항목에서 「기존 자료 6개는 백필하지 않는다 — 다음에 열면 복습
자료를 새로 만든다」고 적었는데 **틀렸다.** 취약 재학습(`kind: review`,
`round: null`)은 원래 `topic_contents` 를 다시 읽는 경로다. 새로 만들지
않는다. 그래서 막혔다.

### 규칙

**모델에게 요구하는 것과 디스크에서 견디는 것은 다르다.**

| | 스키마 | `solution` |
|---|---|---|
| 모델 응답 검증 | `ContentSchema` · `ReviewSchema` | **필수** |
| 저장된 행 읽기 | `StoredContentSchema` · `StoredReviewSchema` | 선택 |

새 필드는 생성에서 필수, 읽기에서 선택이다. 옛 자료는 그 칸이 빈 채로 계속
쓰인다 — `solutionsOf` 가 없는 것을 빼고 주고, 화면은 없으면 안 그린다.

저장 스키마가 아무거나 받는다는 뜻은 아니다. 형식이 깨진 것은 여전히
거른다 — 느슨해진 것은 **새로 생긴 필드 하나**뿐이다.

### 테스트

「예전 형식으로 저장된 자료가 계속 읽히는가」를 박았다. 앞으로 필수 필드를
더하면 거기서 먼저 깨진다. 같은 테스트가 「그래도 모델에게는 요구하는가」도
함께 단언한다 — 느슨하게 만들다가 생성 쪽까지 같이 풀리면 새 자료에서
해설이 조용히 사라진다.

### 남는 것

옛 자료 6개에는 해설이 없다. 앱은 돌아가지만 **지금 막혀 있는 그 6개가
정확히 해설이 가장 필요한 것들이다**(30 · 18 · 46 · 41 · 59점). 백필을
할지는 사용자가 정한다 — 6회 호출, 약 $0.004.

## 2026-09-27 — 초기화 대신 해설만 채운다

회귀를 고친 뒤 남은 질문은 「그럼 전부 초기화하는 게 낫나」였다.
답하기 전에 자료 6개의 상태를 실제로 쟀다.

```
09-04  cs.prog.variables-types              783자  한글 537 / 영문  12   ✅ 평서체
09-04  english.grammar.sentence-structure   825자  한글 444 / 영문 150   ✅ 평서체
09-04  english.vocab.academic-basics        661자  한글   0 / 영문 557   ✅ 평서체
09-14  math.calc.rate-of-change             820자  한글 410 / 영문  47   ✅ 평서체
09-14  math.foundation.coordinates          808자  한글 480 / 영문  34   ✅ 평서체
09-14  math.foundation.expressions          661자  한글 404 / 영문  21   ✅ 평서체
```

**전부 지금 프롬프트로 만들어진 멀쩡한 자료다.** 덤으로 어휘 레시피가
실호출에서 확인됐다 — `english.vocab.academic-basics` 의 지문이 한글 0자,
영문 557자다. 순수 영어 글이 나왔다.

빠진 것은 해설 하나뿐이다. 초기화하면 3주치 진도(숙련도·반복해 틀린
개념·복습 예약·시도 횟수)와 멀쩡한 자료 6개를 버리고 같은 돈을 다시 쓴다.
**적응형 커리큘럼은 「무엇을 틀렸나」에서 계획을 만든다** — 그걸 지우면
설계의 전제가 사라진다.

### 채우기는 생성이 아니다

`lib/llm/solutions.ts` — 지문과 문제와 루브릭을 **주고** 해설만 받는다.

지문과 문제를 다시 만들지 않는 것이 핵심이다. 학습자가 이미 그 지문을 읽고
그 문제에 답했다. 새로 만들면 이미 쓴 답과 채점 기록이 가리키는 문제가
달라진다 — 그건 복구가 아니라 덮어쓰기다. 테스트가 「지문과 문제가 그대로
인가」를 단언한다.

### 스크립트가 캡 밖으로 새지 않는다

`reserve()` 를 그대로 지난다. 방어선에 뒷문을 내면 그게 방어선이 아니다.
Topic 하나에 호출 하나이고, 캡에 걸리면 거기서 멈춘다. 실패하면 예약을
되돌리고(돈이 안 나갔다), 검증 실패는 되돌리지 않는다(이미 나갔다) —
`ensure.ts` 와 같은 규칙이다.

### 절반만 채우지 않는다

모델이 문제 하나를 빠뜨리면 **아무것도 쓰지 않는다.** 절반만 채워두면
다음에 다시 돌릴 때 무엇이 남았는지 알기 어렵고, 화면이 들쭉날쭉해진다.

### 로직은 lib 에, 스크립트는 얇게

`scripts/backfill-solutions.mjs` 는 부르기만 한다. 돈이 나가는 판단은 전부
테스트가 붙은 `lib/llm/solutions.ts` 에 있다. 인자 없이 돌리면 **무엇을
채울지만 보여주고 끝난다** — `--run` 이 있어야 호출한다.

## 2026-09-27 — 수학이 전부 「설명한다」였다

「커리큘럼 Topic 채우기」를 하려고 실제로 재보니, 내가 HANDOFF 에 적어둔
「65개의 goal·keywords 는 있지만 내용이 얇다」가 **틀렸다.** goal 은 오히려
잘 쓰여 있다 — 「미분계수가 접선의 기울기인 이유를 극한으로 설명한다」는
구체적이고 채점 가능하다.

진짜 구멍은 셋이었다.

### ① 90일 목표인데 커리큘럼은 30일치

```
30일 목표 → Topic 51개 · 1375분 → 하루 60분이면 23일치
90일 목표 → Topic 65개 · 1760분 → 하루 60분이면 30일치
```

복습이 슬롯을 먹으므로 실제로는 더 오래 가지만 언젠가 신규가 바닥난다.
이번에는 손대지 않았다 — 당장의 학습을 막는 것이 아니다.

### ② 수학 19개가 전부 `kind: concept` 이고 목표가 전부 "설명한다"

그런데 학습자가 실제로 틀린 것은 전부 **계산**이었다.

| Topic | 점수 | `weak_concepts` |
|---|---|---|
| 함수의 변화율 | 46 | **함수의 값 계산 방법** · 기울기 개념 · **기울기 계산 방법** |
| 좌표와 그래프 | 59 | **기울기 계산 방법** |
| 식의 계산 | 41 | 인수분해와 분배법칙의 관계 |

**개념을 설명할 줄 아는 것과 손으로 풀 줄 아는 것은 다르다.**
`kind: practice` 레시피는 진작 써뒀는데 그걸 쓰는 Topic 이 0개였다.

연습 Topic 4개를 넣고 개념 Topic 의 `remediation` 으로 걸었다.
못 넘기면 정확히 그 드릴로 내려간다.

### ★ 연습 Topic 은 선수를 갖지 않는다

설계 중에 함정을 하나 피했다. 「식 계산 연습」의 선수를 「식의 계산」으로
걸면, **못 넘겨서 연습으로 내려가는 바로 그 상황에서 연습이 잠긴다** —
`isUnlocked` 는 선수가 전부 기준점을 넘어야 열기 때문이다. 보충 경로가
막다른 길이 된다.

연습은 **내려가는 곳이지 올라가는 곳이 아니다.** 테스트가 이걸 잠근다.
「아무도 안 가리키는 연습은 없다」도 같이 — 그건 죽은 Topic 이다.

### ③ `math/a-foundation.yaml` 의 주석이 지금은 안 맞는다

> 계획 엔진이 여기 Topic 을 고르는 경로는 단 하나 — 다른 Topic 의
> remediation 에서 끌려 나오는 것뿐이다.

`includedLevels(90)` 이 `optional` 까지 포함하므로, 목표가 90일이면 기초
수학이 **본선에 들어온다.** 학습자가 좌표·식을 `new` 로 배운 것이 그것이다.
60일 이하에서는 주석대로 동작한다. 의도된 동작으로 보이므로 고치지 않고
적어만 둔다 — 「여유가 있으면 기초도 본다」는 말이 된다.

### 확인

실제 진도로 보충 경로가 열리는지 확인했다:

```
함수의 변화율  46점 · remediation → 변화율 계산 연습 (0/75) [practice] · 함수
좌표와 그래프  59점 · remediation → 기울기 계산 연습 (0/75) [practice]
식의 계산      41점 · remediation → 식 계산 연습 (0/75) [practice]
```

## 2026-09-27 — 연습 실호출에서 나온 결함 둘

`practice` 레시피의 첫 실호출(`math.foundation.slope-drill`, $0.000784).
대체로 성공이다 — 지문이 짧아졌고, 문제가 전부 계산이고, 난이도가 올라가고,
해설이 **생성 경로에서** 처음 나왔고, KaTeX 가 살아 있었다.

결함이 둘 보였다.

### ① 「3~5단계」가 빈 단계를 불렀다

```
1. 두 점의 좌표를 확인한다.
2. 기울기 계산 공식을 사용한다.   ← 아무 결과도 안 남는다
3. y좌표 차이를 계산한다.
4. x좌표 차이를 계산한다.
5. 결과를 나누어 기울기를 구한다.
```

백필 때도 같았으니 **2/2 로 재현**이다. 단순 계산에 5단계는 과하고,
「공식을 사용한다」는 아무 정보도 옮기지 않는다. **개수를 지정한 것이
오히려 칸을 채우게 만들었다.**

지침을 바꿨다 — 「필요한 만큼만. 개수를 채우려 하지 마라. **한 단계는 하나의
동작이고 그 동작의 결과가 단계 안에 드러나야 한다**」. 그리고 나쁜 예와 좋은
예를 나란히 붙였다. `VOICE_RULE` 에서 예시를 붙이니 지켜졌던 것과 같은 방법이다.

### ② 문제 유형 enum 이 개념 학습용이었다

```
[concept] 기울기가 3인 직선의 식을 구할 때 필요한 정보는? 설명하라.
```

연습 Topic 인데 셋 중 하나가 설명 문제가 됐다. **모델 탓이 아니다** —
`recall / concept / application` 중 `concept` 이라는 칸을 주면 개념 문제를
넣는 것이 맞다.

그리고 이 값은 `AnswerForm` 에서 **「기억 / 개념 / 적용」으로 화면에 보인다.**
계산 문제에 「개념」이 붙는 것은 사용자에게 보이는 오류였다.

**유형을 성격마다 다르게 했다.**

| 성격 | 유형 |
|---|---|
| 개념 · 어휘 · 독해 | `recall` · `concept` · `application` |
| 연습 | `basic` · `combined` · `applied` (기본 · 복합 · 응용) |

`CONTENT_JSON_SCHEMA` 상수를 `contentJsonSchema(kind)` 함수로 바꿨다.
`REVIEW_JSON_SCHEMA` · `REVIEW_SYSTEM` 도 같이 — **연습 Topic 의 복습이
설명 문제가 되면 연습이 아니게 된다.**

읽기 스키마(`StoredContentSchema`)는 **여섯 값을 전부 받는다.** 유형을
나누기 전에 저장된 자료가 `concept` 을 들고 있다 — 저장과 생성을 가르는
규칙이 여기서도 똑같이 적용된다.

### 덤 — 중복이 하나 줄었다

문제 배열의 JSON Schema 를 `questionsJson(ids, types)` 하나로 모았다.
콘텐츠와 복습이 같은 모양을 쓰는데 해설 블록까지 두 벌로 복사돼 있었다.
