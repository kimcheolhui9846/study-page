# 3단계 — GPT 연결

설계: [`docs/specs/2026-09-01-adaptive-curriculum-design.md`](../specs/2026-09-01-adaptive-curriculum-design.md) §9 · §10.
1·2단계는 LLM 호출 0회였다. 여기서 처음으로 실제 호출이 붙는다.

**완료 기준:** 실제로 하루를 완주하고, 다음 날 계획이 그 결과를 반영해 달라진다.

## 이 단계의 비용 모양

계획 항목 N개짜리 하루의 호출 수는 **생성이 필요한 항목 수 + 1**이다.

- 콘텐츠 생성 — 항목마다 1회. 단 **이미 있으면 0회** (`topic_contents`
  UNIQUE(topic_id), `review_items` UNIQUE(topic_id, round)).
- 채점 — **계획 전체에 1회.** 항목마다 부르지 않는다.
- 취약 재학습(`kind: review`, `round: null`)은 원래 콘텐츠를 다시 쓰므로 생성 0회.

이 숫자는 `lib/plan/build.ts` 의 `estimateCalls` 가 이미 계산해 `daily_plans.estimated_calls`
에 박아둔 값과 같아야 한다. **어긋나면 계획이 예산을 거짓말한 것이다** — 테스트로 묶는다.

## 실제로 한 것 중 계획에 없던 것

- **채점 응답에서 `score` 제거** (설계 §9.2 는 남기라고 했다). 이유는 DECISIONS.
- **채점 응답을 Topic 배열로 재구성.** 계획 단위로 묶으면 `per_question.id`
  가 Topic 사이에서 충돌한다 (모든 Topic 에 q1 이 있다).
- **`ProgressState.weakConcepts` 추가.** `topic_progress` 에는 있던 컬럼인데
  계획 엔진의 뷰에 없었다. 컨텍스트 조립이 이걸 쓴다.
- **`priorityOf` 의 `overdueDays` → `dueDays` 수정.** 기한 당일의 복습이
  0점이던 결함. DECISIONS 참조.
- **초안 저장 키를 `(subject, dayNo)` → `topicId` 로.**
- **2단계의 수동 점수 입력 제거** (`ScoreEntry` · `POST /api/plan/score`).
  실제 채점이 그 자리를 대신한다. `applyManualScore` 는 테스트용으로 남겼다.
